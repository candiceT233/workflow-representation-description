# Workflow Definition Document (WDD) — Design Specification

## 1. Purpose & Scope

The WDD captures the **logical structure** of a scientific workflow — what it *is*, independent of how it is executed. It is the most stable document in the five-document agent knowledge architecture (WDD → DDD → IODD, with GD and HRD as side inputs). The WDD changes only when the workflow source code changes.

The WDD is generated by giving a workflow codebase to Claude Code. Everything in the WDD must be derivable from static analysis of the source code — no profiling data, no hardware specifics, no deployment decisions.

---

## 2. Document Structure

The WDD is a YAML document with the following top-level sections. YAML is chosen over prose because the downstream consumers are agents, not humans — machine-parseability and unambiguous cross-referencing are paramount.

```yaml
# ============================================================
# WORKFLOW DEFINITION DOCUMENT (WDD)
# ============================================================

metadata:
  wdd_version: "1.0"
  workflow_name: "<human-readable name>"
  workflow_id: "<slug identifier, e.g., deepdrive_md>"
  source_repository: "<URL or path to the codebase analyzed>"
  source_commit: "<git commit hash, if available>"
  generated_by: "claude-code"
  generated_at: "<ISO 8601 timestamp>"
  description: |
    <1–3 sentence summary of what this workflow does and its
    scientific domain.>

# ------------------------------------------------------------
# SECTION A: STAGE CATALOG
# ------------------------------------------------------------
# Stages are logical groupings of tasks that achieve a distinct
# milestone. Stages execute in a defined order (though tasks
# within a stage may run in parallel).

stages:
  - stage_id: "stage:<name>"
    name: "<human-readable stage name>"
    order: <integer, 1-indexed execution order>
    description: |
      <What this stage accomplishes in the workflow.>
    tasks:
      - "<task_id reference>"
      # ...

# ------------------------------------------------------------
# SECTION B: TASK CATALOG
# ------------------------------------------------------------
# Every distinct executable / function / script that appears
# in the workflow. Each task receives a stable identifier.

tasks:
  - task_id: "task:<name>"
    name: "<human-readable name>"
    executable: "<script/binary name, e.g., openmm_simulation.py>"
    stage: "stage:<parent stage name>"
    description: |
      <What this task does functionally — 2–4 sentences.
      Include whether it is compute-dominant, I/O-dominant,
      or balanced, and why.>
    behavioral_notes: |
      <Key I/O-relevant behaviors observable from the code:
      - Does it read all input at startup or stream?
      - Does it write output incrementally or at the end?
      - Does it have internal iteration / checkpointing?
      - Any notable memory patterns (e.g., loads full dataset
        into memory vs. chunked processing)?
      >
    parallelism_model:
      type: "<serial | embarrassingly_parallel | data_parallel | task_parallel>"
      description: |
        <How multiple instances of this task relate to each other.
        E.g., "Each instance processes one chromosome independently"
        or "All instances share a global model and synchronize
        gradients.">
    inputs:
      - "<data_id reference>"
      # ...
    outputs:
      - "<data_id reference>"
      # ...

# ------------------------------------------------------------
# SECTION C: DATA OBJECT REGISTRY
# ------------------------------------------------------------
# Every logical data object that flows through the workflow.
# These are LOGICAL descriptions — not bound to physical paths,
# formats, or storage tiers (that belongs in the DDD/IODD).

data_objects:
  - data_id: "data:<name>"
    name: "<human-readable name>"
    description: |
      <What this data represents scientifically and structurally.>
    category: "<input | intermediate | output | checkpoint | config>"
    persistence: "<transient | stage_scoped | workflow_scoped | persistent>"
    format_hint:
      container: "<HDF5 | netCDF | CSV | tar | plain_binary | text | unknown>"
      datasets: # (for structured formats like HDF5/netCDF)
        - dataset_name: "<name within the container>"
          description: "<what this dataset holds>"
          dtype: "<float32 | int64 | string | variable_length | etc.>"
          shape_hint: "<e.g., [N_frames, N_atoms, 3] or 'scalar' or 'variable'>"
      compression: "<none | gzip | lzf | unknown>"
      layout_hint: "<contiguous | chunked | unknown>"
    cardinality: |
      <How many instances of this data object exist at runtime?
      E.g., "one per chromosome (10 total)", "one per simulation
      task (12 instances)", "single global file".>
    estimated_size_hint: |
      <Order-of-magnitude size if inferrable from the code.
      E.g., "~100 MB per instance" or "small config file, <1 KB".
      Write "unknown" if not determinable from code alone.>

# ------------------------------------------------------------
# SECTION D: PRODUCER–CONSUMER EDGES
# ------------------------------------------------------------
# Every data dependency between tasks. Each edge encodes what
# is produced, what is consumed, and the P–C pattern.

pc_edges:
  - edge_id: "pc:<producer_task>-><consumer_task>:<pattern>"
    producer: "task:<name>"
    consumer: "task:<name>"
    data_objects:
      - "data:<name>"
      # ... (can involve multiple data objects)
    pc_pattern: "<1-1 | 1-n | n-1 | n-n>"
    pc_pattern_rationale: |
      <Why this classification? E.g., "One simulation task
      produces one trajectory file consumed by one contact_map
      task → 1-1." Or "All indiv tasks produce chromosome
      files consumed by a single merge task → n-1.">
    data_flow_description: |
      <Prose description of what data moves across this edge,
      how it is accessed (full read, partial read, streamed),
      and any notable characteristics (e.g., "consumer reads
      only 3 of 4 datasets in the HDF5 file").>
    coupling: "<tight | loose>"
    coupling_rationale: |
      <Tight = consumer cannot begin until producer completes
      and data is fully written. Loose = consumer can begin
      processing partial/streaming output, or there is no
      strict ordering requirement.>

# ------------------------------------------------------------
# SECTION E: WORKFLOW GRAPH TOPOLOGY
# ------------------------------------------------------------
# The DAG structure, expressed as adjacency + classification.
# 

workflow_graph:
  dag_edges:
    - from: "task:<name>"
      to: "task:<name>"
      via: "pc:<edge_id>"
    # ...

  critical_path_hint: |
    <If determinable from code structure, describe the longest
    chain of sequential dependencies. E.g., "simulate → aggregate
    → train → inference forms the critical path; simulate is
    the most parallelizable stage." Write "indeterminate from
    static analysis" if the critical path depends on runtime data.>

  control_flow:
    has_iteration: <true | false>
    iteration_description: |
      <If iterative, describe the loop structure: what triggers
      a new iteration, which stages are repeated, what data
      carries across iterations. E.g., "The workflow repeats
      stages 1–4 for N_iterations, where the inference stage
      output parameterizes the next simulation stage.">
    has_conditional_branches: <true | false>
    conditional_description: |
      <If conditional, describe the branching logic.>

# ------------------------------------------------------------
# SECTION F: WORKFLOW-LEVEL PATTERN CLASSIFICATION
# ------------------------------------------------------------
# Classification per the IPDPS '26 taxonomy.

workflow_patterns:
  primary_pattern: "<cascading | iterative | scatter_gather | pipeline | broadcast | checkpointing | conditional | hybrid>"
  secondary_patterns:
    - "<additional patterns if hybrid>"
  classification_rationale: |
    <Justify the classification by referencing the DAG structure,
    the P–C patterns, and the control flow. E.g., "The workflow
    is primarily cascading (linear stage chain) with a
    scatter-gather sub-pattern in stages 1–2 (1-n scatter from
    initial_data to indiv tasks, n-1 gather into merge).">
  pattern_table_row: |
    <A single-row summary matching the format of Table III from
    the IPDPS '26 paper:
    Workflow | #Stages | #Task Instances | P–C Patterns | Workflow-level I/O Patterns>

# ------------------------------------------------------------
# SECTION G: I/O BEHAVIORAL HINTS
# ------------------------------------------------------------
# Observations about I/O behavior derivable from code inspection
# (not profiling). These help downstream agents prioritize
# investigation areas.

io_behavioral_hints:
  - hint_id: "hint:<short_name>"
    description: |
      <Observation about a potential I/O concern visible in the
      code. E.g., "The aggregate task opens all 12 simulation
      output files sequentially but only reads 3 of 4 HDF5
      datasets from each — potential partial file access waste."
      Or "Checkpoint files are written every iteration but never
      read unless the workflow restarts — candidates for lazy
      write or tiered storage.">
    affected_tasks:
      - "task:<name>"
    affected_data:
      - "data:<name>"
    potential_concern: "<partial_access | format_mismatch | small_file_overhead | unnecessary_serialization | data_reuse | checkpoint_waste | metadata_overhead | unknown>"

# ------------------------------------------------------------
# SECTION H: CROSS-REFERENCE INDEX
# ------------------------------------------------------------
# Machine-readable index for agent navigation.

cross_reference:
  task_to_stage:
    "task:<name>": "stage:<name>"
    # ...
  data_to_producer:
    "data:<name>": "task:<name>"
    # ...
  data_to_consumers:
    "data:<name>":
      - "task:<name>"
    # ...
  stage_execution_order:
    - "stage:<name>"
    # ... (in order)
```

## 3. Design Rationale

**Why YAML over prose?** The WDD is consumed by agents (Tier 1 diagnosis, Tier 2 prescription). Agents need to look up tasks by ID, traverse edges, and filter data objects by category. YAML gives us this for free. A prose document would require an additional parsing step and introduce ambiguity.

**Why `format_hint` in data objects if format belongs in the IODD?** The WDD captures what is *visible in the source code*. If the code writes `h5py.File(...)` with named datasets, that is a logical property of the workflow, not a deployment choice. The IODD captures the *runtime reality* (actual chunk sizes, achieved bandwidth, fragmentation). The `format_hint` in the WDD tells downstream agents what to *expect* and where DaYu-style semantic analysis will be relevant.

**Why `io_behavioral_hints`?** These are the static-analysis equivalent of DaYu's observations. An LLM reading the code can often spot patterns (partial file access, unnecessary aggregation, format mismatches) that would otherwise require profiling to discover. Capturing these hints in the WDD gives diagnosis agents a head start.

**Why `coupling` on P–C edges?** Tight vs. loose coupling directly affects what deployment strategies are feasible (pipelining, co-scheduling). This is inferrable from code (does the consumer wait for a complete file, or can it stream?) and is essential context for the DDD generation step.

**Cardinality and size hints** are approximate and may say "unknown." They are present because even rough estimates help agents reason about storage tier assignments and bandwidth requirements at DDD generation time.

## 4. Claude Code Generation Prompt

The following prompt is designed to be given to Claude Code along with access to the workflow codebase. It should be placed in a `CLAUDE.md` or provided as the initial instruction.

---

````markdown
# TASK: Generate a Workflow Definition Document (WDD)

You are analyzing a scientific workflow codebase to produce a **Workflow Definition Document (WDD)** — a structured YAML document that captures the logical structure of the workflow independent of how it is executed.

## What You Are Producing

A single YAML file (`wdd.yaml`) that fully describes:
1. What stages and tasks exist in this workflow
2. What data objects flow between tasks
3. How tasks depend on each other (producer–consumer edges with pattern classification)
4. The overall workflow structure and pattern classification
5. I/O behavioral hints visible from static code analysis

## Critical Constraints

- **Only include what is derivable from the source code.** Do not speculate about runtime performance, hardware, or deployment strategy.
- **Every entity gets a stable ID** following the convention: `task:<name>`, `data:<name>`, `stage:<name>`, `pc:<producer>-><consumer>:<pattern>`, `hint:<name>`.
- **Classify every P–C edge** using the pattern taxonomy: `1-1` (one producer, one consumer), `1-n` (one producer, many consumers), `n-1` (many producers, one consumer), `n-n` (many producers, many consumers). Always include a rationale.
- **Classify the overall workflow** using the pattern taxonomy: `cascading`, `iterative`, `scatter_gather`, `pipeline`, `broadcast`, `checkpointing`, `conditional`, or `hybrid`. Always include a rationale.
- **For data objects**, capture format hints if visible in code (HDF5 dataset names, data types, shapes) but mark as `unknown` what you cannot determine.
- **Write behavioral notes for every task** focusing on I/O-relevant behavior: how it reads input, how it writes output, whether it streams or batches, internal iteration, memory patterns.

## Analysis Procedure

Follow this sequence. Do not skip steps.

### Step 1: Survey the codebase structure
Read the top-level directory, README, and any workflow orchestration files (e.g., Makefiles, shell scripts, workflow manager configs like Pegasus, Nextflow, Snakemake, Parsl, or custom launchers). Identify:
- The workflow entry point
- How stages/tasks are defined and launched
- Configuration files that parameterize the workflow

### Step 2: Identify all stages and tasks
Walk the orchestration layer to enumerate every distinct executable unit. For each:
- Determine its stage membership (what logical phase it belongs to)
- Read its source code to understand what it does
- Note its inputs and outputs (files read and written)

### Step 3: Build the data object registry
From Step 2, compile a deduplicated list of all data objects. For each:
- Classify as input, intermediate, output, checkpoint, or config
- Determine persistence scope (transient, stage-scoped, workflow-scoped, persistent)
- If the code uses structured formats (HDF5, netCDF), read the file-creation code to extract dataset names, types, and shapes
- Estimate cardinality (how many instances exist) from loop structures or parallelism

### Step 4: Map producer–consumer edges
For each data object, identify which task(s) produce it and which task(s) consume it. For each edge:
- Classify the P–C pattern (1-1, 1-n, n-1, n-n) based on the cardinality of producers and consumers
- Determine coupling (tight vs. loose) by examining whether the consumer requires the producer to fully complete
- Describe what data moves and how it is accessed

### Step 5: Analyze workflow-level patterns
Using the DAG from Step 4:
- Determine if the workflow is cascading (linear chain), iterative (loop), scatter-gather, pipeline, broadcast, conditional, checkpointing, or hybrid
- Identify the critical path if determinable
- Note any iteration/looping control flow

### Step 6: Extract I/O behavioral hints
Re-read the task source code looking for patterns that suggest I/O concerns:
- **Partial file access**: Task opens a file but reads only a subset of its contents
- **Format mismatch**: Task uses chunked HDF5 for small, sequentially-accessed data (or contiguous for random access)
- **Small file overhead**: Many small files created where a single larger file could suffice
- **Unnecessary serialization**: Aggregation step that exists only to combine files for a single consumer
- **Data reuse**: Same data read by multiple tasks (inter-task reuse) or re-read by the same task (intra-task reuse)
- **Checkpoint waste**: Checkpoint files written but rarely/never read in the normal execution path
- **Metadata overhead**: Many datasets per file or many small files causing metadata-heavy I/O

### Step 7: Assemble and validate
Write the complete `wdd.yaml`. Then validate:
- Every task references valid data_ids in its inputs/outputs
- Every data_id appears in at least one task's inputs or outputs
- Every pc_edge references valid task_ids and data_ids
- The cross-reference index is consistent with the body
- The stage execution order matches the DAG dependencies

## Output

Produce a single file: `wdd.yaml`

If any section requires assumptions, state them explicitly in the relevant `description` or `rationale` field with the prefix `[ASSUMPTION]`.

If the codebase is incomplete or you cannot determine a value, use `"unknown"` and add a note explaining what information is missing.

## Reference: Pattern Taxonomy

### P–C Patterns (per-edge)
| Pattern | Description | Example |
|---------|-------------|---------|
| 1-1 | One producer writes data read by one consumer | Simulation → post-processing |
| 1-n | One producer's data shared across multiple consumers | Static input used by many analysis tasks |
| n-1 | Several producers write parts consumed by one task | Aggregation of parallel task outputs |
| n-n | Multiple producers and consumers with shared I/O | Parallel ML training, ensemble workflows |

### Workflow-Level Patterns
| Pattern | Description | Typical P–C Structures |
|---------|-------------|----------------------|
| Cascading | Linear chain of stages | Any |
| Iterative | Repeats computation with prior output as input | Often 1-1; may include others |
| Conditional | Tasks access data only if conditions are met | Usually 1-1 or 1-n |
| Checkpointing | Saves task state for restart/recovery | Usually 1-1; may be n-1 |
| Broadcast | One task provides shared input to many | Typical 1-n |
| Scatter-Gather | Data distributed to parallel tasks, then merged | 1-n scatter; n-1 or n-n gather |
| Pipeline | Stages overlap in time with streaming data | 1-1 or 1-n with loose coupling |
| Hybrid | Combination of the above | Mixed |
````

## 5. Example: DeepDriveMD (Abbreviated)

To ground the schema, here is a partial WDD for the DeepDriveMD workflow based on what we know from the research papers:

```yaml
metadata:
  wdd_version: "1.0"
  workflow_name: "DeepDriveMD"
  workflow_id: "deepdrive_md"
  source_repository: "https://github.com/DeepDriveMD/DeepDriveMD-pipeline"
  generated_by: "claude-code"
  description: |
    Deep learning-driven molecular dynamics simulation workflow
    for protein folding. Integrates MD simulation with ML training
    and inference in an iterative loop to steer simulations toward
    biologically relevant conformations.

stages:
  - stage_id: "stage:simulation"
    name: "Molecular Dynamics Simulation"
    order: 1
    description: "Run OpenMM simulations producing trajectory data."
    tasks: ["task:openmm"]
  - stage_id: "stage:aggregation"
    name: "Data Aggregation"
    order: 2
    description: "Consolidate simulation outputs into a single file."
    tasks: ["task:aggregate"]
  - stage_id: "stage:training"
    name: "ML Model Training"
    order: 3
    description: "Train a neural network on aggregated simulation data."
    tasks: ["task:train"]
  - stage_id: "stage:inference"
    name: "Inference"
    order: 4
    description: "Run inference to select new simulation starting points."
    tasks: ["task:inference"]

tasks:
  - task_id: "task:openmm"
    name: "OpenMM Simulation"
    executable: "openmm_simulation.py"
    stage: "stage:simulation"
    description: |
      Runs molecular dynamics simulation using OpenMM. Generates
      HDF5 files containing contact maps, point clouds, FNC, and
      RMSD datasets. I/O-dominant at output: writes structured
      scientific data at simulation completion.
    behavioral_notes: |
      Each task instance writes one HDF5 file with four datasets.
      Output is written at task completion (not streamed).
      No checkpoint mechanism in normal execution path.
    parallelism_model:
      type: "embarrassingly_parallel"
      description: "Each instance simulates an independent trajectory."
    inputs: ["data:simulation_config"]
    outputs: ["data:trajectory_h5"]

  - task_id: "task:aggregate"
    name: "Aggregate"
    executable: "aggregate.py"
    stage: "stage:aggregation"
    description: |
      Reads all simulation HDF5 outputs and consolidates four
      datasets (contact_map, point_cloud, fnc, rmsd) into a
      single aggregated HDF5 file. I/O-dominant: reads many
      files, writes one.
    behavioral_notes: |
      Opens all simulation output files sequentially. Reads all
      four datasets from each file. Writes a single aggregated.h5.
      This is a serialization bottleneck — all data must pass
      through one task.
    parallelism_model:
      type: "serial"
      description: "Single task aggregates all simulation outputs."
    inputs: ["data:trajectory_h5"]
    outputs: ["data:aggregated_h5"]

  # ... (task:train and task:inference follow similar structure)

data_objects:
  - data_id: "data:trajectory_h5"
    name: "Simulation Trajectory"
    description: "Per-simulation HDF5 output with structural analysis data."
    category: "intermediate"
    persistence: "stage_scoped"
    format_hint:
      container: "HDF5"
      datasets:
        - dataset_name: "contact_map"
          description: "Pairwise distance matrix for protein residues"
          dtype: "float32"
          shape_hint: "[N_frames, N_residues, N_residues]"
        - dataset_name: "point_cloud"
          description: "3D coordinates of C-alpha atoms"
          dtype: "float32"
          shape_hint: "[N_frames, N_atoms, 3]"
        - dataset_name: "fnc"
          description: "Fraction of native contacts"
          dtype: "float32"
          shape_hint: "[N_frames]"
        - dataset_name: "rmsd"
          description: "Root mean square deviation from reference"
          dtype: "float32"
          shape_hint: "[N_frames]"
      layout_hint: "chunked"
    cardinality: "One per simulation task (12 instances typical)."
    estimated_size_hint: "~50–200 MB per instance"

pc_edges:
  - edge_id: "pc:openmm->aggregate:n-1"
    producer: "task:openmm"
    consumer: "task:aggregate"
    data_objects: ["data:trajectory_h5"]
    pc_pattern: "n-1"
    pc_pattern_rationale: |
      All 12 parallel simulation tasks produce trajectory files
      consumed by a single aggregate task.
    data_flow_description: |
      Aggregate reads all four HDF5 datasets from each simulation
      output file. Files are accessed sequentially.
    coupling: "tight"
    coupling_rationale: |
      Aggregate cannot begin until all simulation tasks have
      completed and written their output files.

workflow_patterns:
  primary_pattern: "hybrid"
  secondary_patterns: ["iterative", "cascading"]
  classification_rationale: |
    The workflow is primarily iterative — stages 1–4 repeat for
    N iterations, with inference output steering the next round
    of simulations. Within each iteration, the four stages form
    a cascading (linear chain) structure.
  pattern_table_row: |
    DeepDriveMD | 4 | 74 | n-1, 1-1 | Checkpointing, Iterative, Conditional

io_behavioral_hints:
  - hint_id: "hint:partial_access_training"
    description: |
      The training task reads the aggregated HDF5 file but only
      uses three of four datasets (point_cloud, fnc, rmsd),
      excluding the largest dataset contact_map. This means the
      aggregation step processes and writes contact_map data that
      is never consumed by training — potential partial file
      access waste.
    affected_tasks: ["task:train", "task:aggregate"]
    affected_data: ["data:aggregated_h5", "data:trajectory_h5"]
    potential_concern: "partial_access"

  - hint_id: "hint:chunked_layout_small_files"
    description: |
      Simulation outputs use chunked HDF5 layout, but the per-task
      file sizes are relatively small. Chunked layout adds metadata
      overhead and extra I/O operations for small files where
      contiguous layout would allow single-operation reads.
    affected_tasks: ["task:openmm"]
    affected_data: ["data:trajectory_h5"]
    potential_concern: "format_mismatch"

  - hint_id: "hint:unnecessary_serialization"
    description: |
      The aggregate task introduces a serialization point — all
      parallel simulation outputs must be combined into one file
      before training can begin. If the training task could
      directly read from multiple simulation files (or if
      aggregation were parallelized), this bottleneck could
      be reduced.
    affected_tasks: ["task:aggregate"]
    affected_data: ["data:aggregated_h5"]
    potential_concern: "unnecessary_serialization"
```

## 6. Validation Checklist

After generation, verify the WDD against these criteria:

1. **Completeness**: Every file read/written in the codebase is represented as a data object
2. **Consistency**: Every `data_id` referenced in tasks also appears in `data_objects`; every `task_id` in edges appears in `tasks`
3. **Pattern accuracy**: P–C pattern classifications match the actual producer/consumer cardinalities
4. **No deployment leakage**: The WDD contains zero references to specific hardware, storage tiers, node counts, or performance targets
5. **Cross-reference integrity**: The `cross_reference` section matches the body content exactly
6. **Assumption transparency**: Every value that required guesswork is prefixed with `[ASSUMPTION]`
