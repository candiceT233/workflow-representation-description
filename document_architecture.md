# Agent Knowledge Document Architecture

## Overview

This document defines the structured document architecture that feeds knowledge to agents operating within the workflow I/O characterization and optimization system. The architecture decomposes the full problem space into five documents with clean separation of concerns, well-defined dependencies, and one-to-many relationships that capture the natural variation across deployments and hardware targets.

The core insight is that a single workflow can be deployed many ways depending on performance goals, and a single deployment can exhibit different I/O behavior depending on the hardware it runs on. The document architecture mirrors this factorization, giving agents precisely scoped context for each tier of reasoning.

## Document Definitions

### 1. Workflow Definition Document (WDD)

**Purpose:** Capture the logical structure of a workflow — what it *is*, independent of how it is executed.

**Source:** Generated from the workflow source code (e.g., by giving the codebase to Claude Code and having it produce the document).

**Contents:**

- Workflow graph topology: the full task DAG and its connectivity.
- Task catalog: for each task, a name, description, functional role, and key behavioral notes (e.g., "contact_map performs pairwise distance computation over trajectory frames; I/O dominant").
- Edge semantics: for each connection between tasks, the nature of the data dependency — what is produced, what is consumed, the P–C pattern classification (1-1, 1-n, n-1, n-n).
- Workflow-level pattern classification: cascading, iterative, scatter-gather, pipeline, or hybrid, following the IPDPS '26 taxonomy.
- File and dataset registry: enumeration of the data objects that flow through the workflow, with logical descriptions (not yet bound to physical formats or paths).

**Stability:** High. The WDD changes only when the workflow code itself changes. It is the most stable document in the architecture.

**Analogy to existing tools:** This is essentially the DFL-DAG from DataLife, enriched with semantic descriptions and pattern classifications from the IPDPS '26 characterization.

---

### 2. Goal Document (GD)

**Purpose:** Capture the operator's performance objectives and constraints that motivate a particular deployment strategy.

**Source:** Provided by the user/operator or derived from SLA requirements.

**Contents:**

- Target throughput (e.g., "sustained 10 GB/s input ingestion").
- Latency constraints (e.g., "end-to-end pipeline completion within 30 minutes").
- Cost or resource budgets (e.g., "maximum 128 nodes, 2-hour allocation").
- Priority ranking when goals conflict (e.g., "throughput over latency; minimize node-hours as secondary").
- Any hard constraints (e.g., "must use PFS for checkpoint files," "cannot exceed burst buffer capacity").

**Role in the architecture:** The GD is a side input to the WDD → DDD step. It encodes *intent* — why the operator chose a particular deployment configuration. This is critical for prescription agents, which need to understand whether a recommendation is compatible with the operator's goals before issuing it.

---

### 3. Deployment Definition Document (DDD)

**Purpose:** Define how a workflow is deployed to achieve a specific set of goals. This is the execution strategy layer — it bridges logical structure and physical realization.

**Source:** Generated by an agent or human operator, given a WDD and a GD.

**Contents:**

- Per-task parallelism: how many instances of each task run concurrently.
- Task-to-node mapping policy: placement constraints, affinity rules, co-scheduling groups.
- Storage tier assignments: which data objects are targeted to which storage tiers (SSD, burst buffer, PFS, in-memory).
- Stage ordering and pipelining decisions: whether stages overlap, batch sizes, iteration counts.
- Co-scheduling groups: which P–C groups are co-located to minimize data movement.
- Replication or caching strategy: whether intermediate data is replicated for fault tolerance or cached for reuse.
- The target SLOs that motivated these choices (back-reference to the GD).

**One-to-many relationship:** A single WDD can have multiple DDDs. For example, the same workflow might have a throughput-optimized DDD (high parallelism, aggressive staging), a cost-optimized DDD (minimal nodes, sequential stages), and a latency-optimized DDD (deep pipelining, in-memory intermediates).

**Key design note:** The DDD is where human or agent *intent* lives. It captures not just what was decided, but why — linking every deployment choice back to the goal that motivated it. This makes the DDD the primary document a prescription agent consults when evaluating whether a recommendation is feasible and aligned.

---

### 4. Hardware Resource Document (HRD)

**Purpose:** Describe the physical hardware on which a deployment will execute — what the system *is*, independent of how it is used.

**Source:** System documentation, facility specifications, or hardware profiling tools.

**Contents:**

- Compute topology: node count, cores per node, memory per node, interconnect topology and bandwidth.
- Storage hierarchy: tiers available (node-local SSD, burst buffer, parallel file system, object store), capacity per tier, bandwidth ceilings per tier.
- Network fabric: interconnect type (InfiniBand, Slingshot, Ethernet), bisection bandwidth, latency characteristics.
- Shared resource contention model: whether storage tiers are shared across jobs, expected contention levels, QoS guarantees if any.
- Known performance characteristics: empirical bandwidth measurements, metadata operation rates, known bottlenecks.

**Role in the architecture:** The HRD is a side input to the DDD → IODD step. It defines the physical constraints within which the I/O behavior materializes. Keeping the HRD separate from the IODD enables feasibility reasoning — an agent can check whether a deployment's storage tier assignments are even possible on the target hardware before generating the IODD.

---

### 5. I/O Definition Document (IODD)

**Purpose:** Capture the concrete I/O and communication semantics that emerge when a specific deployment runs on specific hardware.

**Source:** Generated from profiling (DataLife, DaYu, Darshan) or predicted by an agent given a DDD and HRD.

**Contents:**

- Per-task I/O profile: for each task instance, the file systems accessed, access patterns (sequential/random, read/write ratios), request sizes, operation counts, bandwidth achieved.
- Communication channel definitions: for each P–C edge, the physical communication path — shared file on PFS, staged through burst buffer, in-memory transfer via MPI, etc.
- Data format specifics: HDF5 dataset layouts, chunking parameters, compression, variable-length data presence — the DaYu semantic layer.
- Temporal I/O behavior: when I/O occurs relative to compute phases, burstiness, overlap potential.
- Contention and interference: observed or predicted cross-task I/O contention, metadata bottlenecks, shared-resource saturation.
- Per-file lifecycle: creation time, last access, access frequency, consumers count — the DataLife lifecycle view.

**One-to-many relationship:** A single DDD can produce different IODDs on different hardware. The same "64-way parallel contact_map staged to burst buffer" deployment will have very different I/O characteristics on a system with NVMe burst buffers versus one with spinning-disk scratch space.

**Analogy to existing tools:** The IODD is the union of DataLife's DFL-G lifecycle annotations, DaYu's SDG/FTG semantic mappings, and Darshan's system-level I/O metrics — all bound to a specific deployment on specific hardware.

## Cross-Referencing Convention

All five documents share a common identifier scheme to enable unambiguous internal referencing:

- **Task IDs:** Every task in the WDD receives a stable identifier (e.g., `task:contact_map`, `task:aggregate_results`). The DDD references these when specifying parallelism and placement. The IODD references these when reporting per-task I/O profiles.
- **File/Dataset IDs:** Every logical data object in the WDD receives an identifier (e.g., `data:trajectory_frames`, `data:contact_matrix`). The DDD references these for storage tier assignments. The IODD references these for format details and lifecycle annotations.
- **P–C Edge IDs:** Every producer–consumer relationship in the WDD receives an identifier encoding the pattern type (e.g., `pc:contact_map->aggregate:1-n`). The DDD references these for co-scheduling decisions. The IODD references these for communication channel definitions.
- **Hardware Tier IDs:** The HRD defines identifiers for each storage tier and compute resource class (e.g., `tier:node_ssd`, `tier:burst_buffer`, `tier:pfs`). The DDD references these for tier assignments. The IODD references these for concrete I/O paths.
- **Goal IDs:** The GD assigns identifiers to each objective (e.g., `goal:throughput_10gbs`, `goal:max_nodes_128`). The DDD back-references these to justify deployment choices.

This convention ensures that any entity mentioned in one document can be traced across all others, making the full document set machine-parseable and agent-navigable.

## Dependency Graph

```
                  ┌──────────┐
                  │   GD     │
                  │  (Goal)  │
                  └────┬─────┘
                       │ side input
                       ▼
 ┌──────────┐    ┌──────────┐    ┌──────────┐
 │   WDD    │───▶│   DDD    │───▶│   IODD   │
 │(Workflow)│ 1:N│(Deploy)  │ 1:N│  (I/O)   │
 └──────────┘    └──────────┘    └──────────┘
                       ▲
                       │ side input
                  ┌────┴─────┐
                  │   HRD    │
                  │(Hardware)│
                  └──────────┘
```

- **WDD → DDD** is one-to-many: one workflow, multiple deployment strategies.
- **DDD → IODD** is one-to-many: one deployment, different I/O realizations per hardware target.
- **GD** is a side input to the WDD → DDD step (motivates deployment choices).
- **HRD** is a side input to the DDD → IODD step (constrains physical realization).

## Agent Context Scoping

The document architecture directly addresses the context window / reasoning scope question from the agent research notes. Different agent tiers consume different subsets of the document stack:

| Agent Tier | Primary Documents | Role |
|---|---|---|
| Tier 1: Diagnosis (Offline) | WDD + IODD | Match observed I/O patterns to the taxonomy. The WDD provides structural context; the IODD provides empirical evidence. |
| Tier 2: Prescription (Advisory) | WDD + DDD + IODD + GD | Recommend optimizations. Needs the full picture: what the workflow is (WDD), how it's deployed (DDD), what I/O emerged (IODD), and what the operator wants (GD) to ensure recommendations are compatible. |
| Tier 3: Runtime Orchestration (Online) | DDD + IODD + HRD | Act on live telemetry within deployment constraints. The DDD defines what's allowed; the IODD defines the current state; the HRD defines what's physically possible. |

This scoping ensures agents receive enough context to make informed decisions without being overwhelmed by the full complexity of the workflow graph — directly resolving the "context data structure bottleneck" identified as a central challenge.

## Generation Pipeline

The documents are generated in dependency order:

1. **WDD** — generated from workflow source code (e.g., by an LLM analyzing the codebase, or by DataLife's DFL-G construction enriched with semantic annotations).
2. **GD** — provided by the operator or derived from facility/project SLA requirements.
3. **HRD** — generated from system documentation or hardware profiling.
4. **DDD** — generated by a human operator or a prescription agent, given a WDD + GD. This is a key decision point where agent assistance adds value.
5. **IODD** — generated from profiling data (DataLife + DaYu + Darshan) after execution, or predicted by an agent given a DDD + HRD for planning purposes.

---

## Summary

Given a WDD, a GD, a DDD, an HRD, and an IODD, the entire agent system has a properly structured and internally referenced knowledge base. Each document has a clear scope, a defined generation source, and explicit cross-references to the others. The one-to-many relationships (WDD → DDDs, DDD → IODDs) naturally capture the variation across deployment strategies and hardware targets, while the side inputs (GD, HRD) make the motivation and constraints for each decision explicit and traceable.
