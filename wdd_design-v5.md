# Workflow Definition Document (WDD) — Design Specification
# Version: 5.0  |  Part of the WIDGET Five-Document Architecture

---

## 1. Purpose & Scope

The WDD captures the **logical structure** of a scientific workflow — what it *is*, independent of how it is executed. It is the most stable document in the five-document agent knowledge architecture (WDD → DDD → IODD, with GD and HRD as side inputs). The WDD changes only when the workflow source code changes.

The WDD is generated by giving a workflow codebase to Claude Code. Everything in the WDD must be derivable from static analysis of the source code — no profiling data, no hardware specifics, no deployment decisions.

**What belongs in the WDD:** stage structure, task catalog, task semantics, parallelism model, producer-consumer edges with coupling, workflow-level pattern classification, data object registry with format hints, I/O behavioral hints, execution profiles, and generation provenance.

**What does not belong in the WDD:** parallelism instance counts, storage tier assignments, memory estimates, placement policies, hardware constraints, operator goals, per-run I/O profiles, or observed bandwidth. Those belong in the DDD, HRD, GD, and IODD respectively.

---

## 2. Field Status Model

Every field carries a `_status` annotation telling the generating agent what to do with it.

| Status | Meaning |
|--------|---------|
| `required_static` | Extract from source code via static analysis. If extraction fails, escalate to `required_static_ask`. |
| `required_static_ask` | Cannot be reliably inferred from code. Agent **must** prompt the scientist before proceeding. |

**Completeness Gate** — before the WDD is considered complete, verify:
- All `required_static` and `required_static_ask` fields are non-null
- `workflow_graph.integrity_hash` is current
- All `required_task_sets` in execution_profiles were auto-derived (never manually specified)
- `translation_metadata.field_confidence_records` has one entry per agent-inferred field
- Any `requires_human_review: true` field has been reviewed or explicitly deferred by the scientist

---

## 3. Document Structure

The WDD is a single YAML file (`wdd.yaml`) with the following top-level sections.

```
metadata            — identity, versioning, provenance, workflow-level pattern
stages              — logical stage groupings (Section A)
tasks               — task catalog with behavioral and parallelism descriptions (Section B)
data_objects        — logical data registry with format hints and lifecycle (Section C)
pc_edges            — producer-consumer edges with coupling and pattern (Section D)
workflow_graph      — derived DAG, control flow, cross-reference index (Section E)
workflow_patterns   — workflow-level pattern classification (Section F)
io_behavioral_hints — static-analysis-visible I/O concerns (Section G)
execution_profiles  — named partial execution subsets (Section H)
translation_metadata — generation provenance and confidence records (Section I)
```

## 4. Schema

```yaml
# ============================================================
# WORKFLOW DEFINITION DOCUMENT (WDD)
# Schema: wdd-5.0  |  WIDGET Document Architecture v5
# ============================================================

metadata:
  # --- Identity and versioning ---
  workflow_lineage_id: "<stable UUID — never changes across versions>"
  # _status: required_static
  # Generate once on first compilation. Preserve on all recompiles.
  # Companion documents (DDD, IODD) pin to this ID + a specific version.

  version: "<semantic version, e.g., 1.0.0>"
  # _status: required_static
  # Increment on structural changes (task added/removed, edge changed).
  # Data enrichments (measured sizes) update in place without incrementing.

  version_notes: "<changelog entry — required when version increments>"
  # _status: required_static

  deprecated: <true | false>
  # _status: required_static
  # If true, companion documents must not use this version for new deployments.

  # --- Human-readable identity ---
  workflow_name: "<human-readable name>"
  # _status: required_static

  workflow_description: |
    <1–3 sentence summary: scientific problem, domain, inputs, outputs.
    Quality check: >20 words, domain-specific nouns required.>
  # _status: required_static_ask
  # Prompt: "Please describe this workflow. Include: what scientific problem it
  # solves, what domain it belongs to, what data it starts from, and what
  # results it ultimately produces."

  # --- Source provenance ---
  source_repository: "<URL or path to codebase>"
  # _status: required_static

  source_commit: "<git commit hash, or null if unavailable>"
  # _status: required_static

  source_format: "<native | compiled_from_nextflow | compiled_from_pegasus_dax |
                   compiled_from_parsl | compiled_from_slurm | compiled_from_snakemake |
                   compiled_from_swift_t | other>"
  # _status: required_static

  source_file: "<path to primary workflow definition file>"
  # _status: required_static

  # --- Generation metadata ---
  schema_version: "wdd-5.0"
  # _status: required_static — always set to "wdd-5.0"

  generated_by: "<agent name and version, e.g., claude-code-3.7>"
  # _status: required_static

  generated_at: "<ISO 8601 timestamp>"
  # _status: required_static

  last_modified_at: "<ISO 8601 timestamp>"
  # _status: required_static


# ------------------------------------------------------------
# SECTION A: STAGE CATALOG
# ------------------------------------------------------------
# Logical groupings of tasks that achieve a distinct workflow milestone.
# Stages execute in a defined order; tasks within a stage may run in parallel.
# Stages give Tier 1 diagnosis agents a coarser reasoning granularity before
# drilling to task level, and correspond to stage-level analysis in IPDPS '26
# (e.g., temporal hotspots at specific stages, Table III stage counts).

stages:
  - stage_id: "stage:<descriptor>"
    # _status: required_static  |  Format: stage:<descriptor>

    name: "<human-readable stage name>"
    # _status: required_static

    order: <integer, 1-indexed execution order>
    # _status: required_static

    description: |
      <What this stage accomplishes in the workflow.>
    # _status: required_static

    tasks:
      - "<task_id reference>"
    # _status: required_static


# ------------------------------------------------------------
# SECTION B: TASK CATALOG
# ------------------------------------------------------------
# Every distinct executable unit in the workflow.
# The canonical source of truth for all relationships.
# workflow_graph is derived from this section — never edited directly.

tasks:
  - task_id: "task:<descriptor>"
    # _status: required_static
    # Normalize task/process/function name to snake_case from source code.

    name: "<human-readable name>"
    # _status: required_static

    stage: "stage:<descriptor>"
    # _status: required_static  |  stage_id this task belongs to

    executable: "<script/binary name, e.g., openmm_simulation.py>"
    # _status: required_static

    description: |
      <2–4 sentence domain description: what it does in domain terms,
      what data it reads, what it produces, and why it exists in the workflow.
      Quality check: >20 words, domain-specific nouns required.>
    # _status: required_static_ask
    # Attempt inference from docstrings, function names, comments.
    # Prompt if candidate description fails quality check:
    # "What does task '<task_id>' do? Include: what it does in domain terms,
    # what data it reads, what it produces, and why it exists."

    behavioral_notes: |
      <I/O-relevant behaviors observable from the code:
      - Reads all input at startup or streams incrementally?
      - Writes output at completion or incrementally?
      - Internal iteration or checkpointing?
      - Memory patterns: loads full dataset vs. chunked processing?
      - Notable access patterns (random, strided, sequential)?
      Focus on I/O behavior, not scientific meaning.>
    # _status: required_static

    parallelism_model:
      type: "<serial | embarrassingly_parallel | data_parallel | task_parallel>"
      # _status: required_static
      # Infer from: for-loops/map over input sets (embarrassingly_parallel),
      # MPI collectives (data_parallel), task graph fan-out (task_parallel).

      description: |
        <How multiple instances relate to each other.
        E.g., "Each instance processes one chromosome independently."
        Or "All instances share a global model and synchronize gradients.">
      # _status: required_static

    io_dominance: "<compute_bound | io_bound | balanced | unknown>"
    # _status: required_static
    # Infer from ratio of I/O calls to compute operations in script.
    # Write "unknown" if not determinable from code alone.

    output_class: "<intermediate | checkpoint>"
    # _status: required_static_ask
    # Cannot be reliably inferred from code — always ask the scientist.
    # Prompt: "Does task '<task_id>' produce outputs that are scientifically
    # valuable to retain after the workflow completes (checkpoint), or are
    # they only needed to pass data to the next task (intermediate)?"

    inputs:
      - "<data_id reference>"
    # _status: required_static

    outputs:
      - "<data_id reference>"
    # _status: required_static


# ------------------------------------------------------------
# SECTION C: DATA OBJECT REGISTRY
# ------------------------------------------------------------
# Every logical data object flowing through the workflow.
# Logical descriptions — not bound to physical paths or storage tiers.
# Two layers: Semantic (always required) + Lifecycle (DAG-derivable).

data_objects:

  # --- Section C.1: Semantic Layer ---

  - data_id: "data:<descriptor>"
    # _status: required_static  |  Format: data:<descriptor>

    name: "<human-readable name>"
    # _status: required_static

    description: |
      <What this data represents scientifically and structurally.
      Quality check: >20 words, domain-specific nouns required.>
    # _status: required_static_ask

    category: "<input | intermediate | output | checkpoint | config>"
    # _status: required_static
    # input:        external data entering the workflow (no producer task)
    # intermediate: produced by a task, consumed downstream, no standalone value
    # output:       final result consumed outside this workflow
    # checkpoint:   standalone scientific value; must be retained persistently
    # config:       parameter files, run configs — NOT part of the P-C data flow.
    #               Prevents agents from staging or cleaning up config files.

    persistence: "<transient | stage_scoped | workflow_scoped | persistent>"
    # _status: required_static
    # transient:       exists only within one task execution
    # stage_scoped:    exists for the duration of its stage
    # workflow_scoped: exists for the full workflow run
    # persistent:      survives across workflow runs

    format_hint:
      container: "<HDF5 | netCDF4 | CSV | parquet | tar | plain_binary | text | JSON | unknown>"
      # _status: required_static

      datasets:
        # For structured formats (HDF5, netCDF4): list dataset-level details
        # visible in file-creation code. Omit for other formats.
        - dataset_name: "<name within the container>"
          description: "<what this dataset holds>"
          dtype: "<float32 | int64 | string | variable_length | etc.>"
          shape_hint: "<e.g., [N_frames, N_atoms, 3] or 'scalar' or 'variable'>"
      # _status: required_static (omit datasets list if not HDF5/netCDF4)

      compression: "<none | gzip | lzf | lz4 | zstd | blosc | unknown>"
      # _status: required_static

      layout_hint: "<contiguous | chunked | unknown>"
      # _status: required_static

      typical_request_size_kb: <integer or null>
      # _status: required_static
      # Estimated I/O request size from code inspection (e.g., HDF5 chunk size).
      # Null if not determinable from code.

    cardinality: |
      <How many instances exist at runtime?
      E.g., "one per chromosome (10 total)", "one per simulation task (12 instances)",
      "single global file". Used by DDD for storage capacity estimation.>
    # _status: required_static

    estimated_size_hint: |
      <Order-of-magnitude size if inferrable from code.
      E.g., "~50–200 MB per instance" or "small config file, <1 KB".
      Write "unknown" if not determinable from code alone.>
    # _status: required_static

    producer_task: "<task_id or null for external inputs>"
    # _status: required_static

    consumer_tasks:
      - "<task_id>"
    # _status: required_static

  # --- Section C.2: Dataset Lifecycle Layer ---
  # Logical lifecycle properties derivable entirely from DAG topology.
  # Captures when data is created and last used within the workflow structure.

    lifecycle:
      creation_phase: "<task_id whose completion creates this dataset>"
      # _status: required_static  |  Derived from producer_task

      last_consumer_phase: "<task_id of last consumer in topological order>"
      # _status: required_static  |  Derived from consumer_tasks + DAG ordering

      retention_window: "<from task:X completion to task:Y completion>"
      # _status: required_static
      # Span between creation_phase and last_consumer_phase, expressed as
      # task completion events. Derivable from DAG topology alone.

      access_frequency_class: "<once | few_times | repeatedly>"
      # _status: required_static

      consumer_count: <integer>
      # _status: required_static


# ------------------------------------------------------------
# SECTION D: PRODUCER–CONSUMER EDGES
# ------------------------------------------------------------
# Every data dependency between tasks. Encodes the relationship between
# producer and consumer — not just which data objects exist.
#
# coupling describes a structural property of the workflow derivable from
# code: tight = consumer requires producer to fully complete before starting;
# loose = consumer can begin on partial or streaming output.

pc_edges:
  - edge_id: "pc:<producer_task>-><consumer_task>:<pattern>"
    # _status: required_static  |  e.g., pc:openmm->aggregate:n_to_1

    producer: "task:<n>"
    # _status: required_static

    consumer: "task:<n>"
    # _status: required_static

    data_objects:
      - "data:<n>"
    # _status: required_static
    # LIST — one edge may carry multiple datasets simultaneously.
    # E.g., the openmm→aggregate edge in DeepDriveMD carries four HDF5 datasets
    # (contact_map, point_cloud, fnc, rmsd) in one file.
    # Do NOT create one edge per dataset for a single task relationship.

    pc_pattern: "<1_to_1 | 1_to_n | n_to_1 | n_to_n>"
    # _status: required_static

    pc_pattern_rationale: |
      <Why this classification? E.g., "All 12 parallel simulation tasks produce
      trajectory files consumed by a single aggregate task → n_to_1.">
    # _status: required_static

    data_flow_description: |
      <What data moves, how it is accessed (full read, partial read, streamed),
      and any notable characteristics (e.g., "consumer reads only 3 of 4
      datasets in the HDF5 file").>
    # _status: required_static

    coupling: "<tight | loose>"
    # _status: required_static
    # tight: consumer cannot begin until producer fully completes and data is
    #        written. No pipeline overlap is possible.
    # loose: consumer can begin on partial/streaming output. Pipeline overlap
    #        is possible.

    coupling_rationale: |
      <Why this coupling? E.g., "Aggregate cannot begin until all simulation
      tasks have completed — tight." Or "Training reads chunks as they become
      available — loose.">
    # _status: required_static

    communication_pattern: "<shared_file | file_per_producer | in_memory | streaming_channel>"
    # _status: required_static  |  Workflow-level observation from code structure.

    data_volume_class: "<small | medium | large>"
    # _status: required_static
    # small: <1 GB  |  medium: 1–100 GB  |  large: >100 GB
    # Agent-estimated from cardinality × estimated_size_hint.


# ------------------------------------------------------------
# SECTION E: WORKFLOW GRAPH
# ------------------------------------------------------------
# Derived from Task Catalog and P-C Edges. Never edited directly.
# integrity_hash must match pc_edges on every read.

workflow_graph:

  integrity_hash: "<SHA-256 of canonical serialization of all pc_edges>"
  # _status: required_static
  # Mismatch = reject graph and request regeneration.

  last_generated: "<ISO 8601 timestamp>"
  # _status: required_static

  dag_edges:
    - from: "task:<n>"
      to: "task:<n>"
      via: "pc:<edge_id>"
  # _status: required_static  |  Derived from pc_edges

  loop_groups:
    - loop_id: "<descriptive loop identifier>"
      tasks:
        - "task:<n>"
      loop_type: "<static | parameter_sweep | data_driven | convergence>"
      note: "<brief description of the loop structure>"
  # _status: required_static  |  Derived from iteration structures in code

  critical_path_hint: |
    <Longest sequential dependency chain if determinable. Write
    "indeterminate from static analysis" if runtime-dependent.>
  # _status: required_static

  control_flow:
    has_iteration: <true | false>
    # _status: required_static

    iteration_description: |
      <What triggers a new iteration, which stages repeat, what data carries
      across iterations, convergence criterion if any, whether iteration count
      is known at submission time or determined at runtime.>
    # _status: required_static  |  Required when has_iteration = true; null otherwise

    has_conditional_branches: <true | false>
    # _status: required_static

    conditional_description: |
      <What condition is evaluated, which tasks are skipped, what data triggers
      the branch.>
    # _status: required_static  |  Required when has_conditional_branches = true; null otherwise

  stage_execution_order:
    - "stage:<n>"
  # _status: required_static  |  In topological execution order
  # Flat ordered list enabling stage-level reasoning without full DAG traversal.

  cross_reference:
    # Flat lookup table. Removes multi-hop traversal cost for LLMs.
    # Auto-derived — never manually edited.
    task_to_stage:
      "task:<n>": "stage:<n>"
    data_to_producer:
      "data:<n>": "task:<n>"   # null for external inputs
    data_to_consumers:
      "data:<n>":
        - "task:<n>"
  # _status: required_static


# ------------------------------------------------------------
# SECTION F: WORKFLOW-LEVEL PATTERN CLASSIFICATION
# ------------------------------------------------------------
# Classification per the IPDPS '26 taxonomy.

workflow_patterns:
  primary_pattern: "<cascading | iterative | scatter_gather | pipeline |
                    broadcast | checkpointing | conditional | hybrid>"
  # _status: required_static

  secondary_patterns:
    - "<additional pattern>"
  # _status: required_static  |  Required when primary_pattern = hybrid; [] otherwise

  classification_rationale: |
    <Justify by referencing DAG structure, P-C patterns, and control flow.>
  # _status: required_static

  pattern_table_row: |
    <Single-row summary: Workflow | #Stages | #Task Instances | P-C Patterns | Workflow-level I/O Patterns>
  # _status: required_static


# ------------------------------------------------------------
# SECTION G: I/O BEHAVIORAL HINTS
# ------------------------------------------------------------
# Static-analysis-visible I/O concerns. Code-inspection equivalent of
# DaYu's runtime observations. Gives Tier 1 diagnosis agents a pre-loaded
# list of suspicions before any profiling has run — drawn from IPDPS '26
# findings.
#
# Concern vocabulary:
#   partial_access            task reads only a subset of a file's contents
#   format_mismatch           layout choice mismatched to access pattern
#   small_file_overhead       many small files where one larger file would suffice
#   unnecessary_serialization aggregation exists only to combine for one consumer
#   data_reuse                same data read by multiple tasks or re-read intra-task
#   checkpoint_waste          checkpoints written but not read in normal path
#   metadata_overhead         many small files or datasets causing metadata-heavy I/O
#   unknown                   concern visible but does not fit above

io_behavioral_hints:
  - hint_id: "hint:<short_name>"
    # _status: required_static

    description: |
      <Specific observation. Name the task, name the file/dataset, describe
      the pattern. E.g., "The aggregate task opens all 12 simulation output
      files sequentially but reads only 3 of 4 HDF5 datasets from each —
      potential partial file access waste.">
    # _status: required_static

    affected_tasks:
      - "task:<n>"
    # _status: required_static

    affected_data:
      - "data:<n>"
    # _status: required_static

    potential_concern: "<partial_access | format_mismatch | small_file_overhead |
                        unnecessary_serialization | data_reuse | checkpoint_waste |
                        metadata_overhead | unknown>"
    # _status: required_static


# ------------------------------------------------------------
# SECTION H: EXECUTION PROFILES
# ------------------------------------------------------------
# Named partial execution subsets representing scientifically meaningful
# stopping points. Agent proposes from checkpoint tasks; scientist confirms.

execution_profiles:
  - profile_name: "<short identifier, e.g., tracks_only, full>"
    # _status: required_static_ask
    # Propose from checkpoint tasks: "I found checkpoint tasks at [task list].
    # I suggest profiles: [proposed_list]. Are these meaningful stopping points?"

    terminal_task_id: "task:<n>"
    # _status: required_static  |  Last task required for this profile

    description: |
      <What scientific results this profile produces.>
    # _status: required_static_ask

    required_task_set:
      - "task:<n>"
    # _status: required_static
    # AUTO-DERIVED ONLY by backward DAG traversal from terminal_task_id.
    # Never manually specified. Recompute whenever dag_edges changes.

    output_dataset_ids:
      - "data:<n>"
    # _status: required_static
    # Checkpoint datasets produced by tasks in required_task_set.


# ------------------------------------------------------------
# SECTION I: TRANSLATION METADATA
# ------------------------------------------------------------
# Full provenance of how this WDD was produced.

translation_metadata:
  source_format: "<same as metadata.source_format>"
  source_file: "<same as metadata.source_file>"
  translation_tool: "<agent name and version>"
  translation_timestamp: "<ISO 8601 timestamp>"

  unmapped_fields:
    - field_path: "<dotted path, e.g., tasks[0].behavioral_notes>"
      reason: "<why this field could not be extracted>"
  # Empty list is valid.

  round_trip_gaps:
    - field_path: "<dotted path>"
      note: "<e.g., 'semantic_description has no representation in Pegasus DAX'>"

  quality_warnings:
    - field_path: "<dotted path>"
      warning: "<e.g., 'description too short (8 words), domain nouns absent'>"
  # Review flags, not blockers.

  field_confidence_records:
    # One record per agent-inferred field. Programmatically auditable.
    # At minimum cover: all description fields, all pc_pattern fields,
    # workflow_patterns, io_dominance per task, behavioral_notes per task.
    - field_path: "<dotted path>"
      filled_by: "<agent name>"
      confidence_level: "<high | medium | low | inferred>"
      confidence_reason: "<brief justification>"
      requires_human_review: <true | false>
```

## 5. Generation Procedure

Place the following in `CLAUDE.md` or provide as the initial instruction alongside the workflow codebase.

**Step 1 — Survey codebase structure.**
Read the top-level directory, README, and orchestration files (Makefile, shell scripts, Nextflow `main.nf`, Pegasus DAX, Parsl app file, Snakemake `Snakefile`, Slurm submission script). Identify: workflow entry point, how stages/tasks are defined and launched, configuration files.

**Step 2 — Identify all stages and tasks.**
Walk the orchestration layer to enumerate every stage and every distinct executable unit. For each task: determine stage membership, read source code, note inputs and outputs.

**Step 3 — Build the data object registry.**
Compile a deduplicated list of all data objects. Classify each as input/intermediate/output/checkpoint/config. For HDF5/netCDF4, read file-creation code to extract dataset names, dtypes, and shapes. Estimate cardinality from loop structures. Derive lifecycle fields (creation_phase, last_consumer_phase, retention_window) from DAG topology.

**Step 4 — Map producer-consumer edges.**
For each data object, identify producers and consumers. Classify P-C pattern. Determine coupling by examining whether the consumer requires the full file or can stream partial output. Note when a single edge carries multiple datasets. Describe what data moves and how it is accessed.

**Step 5 — Analyze workflow-level patterns.**
From the DAG: classify primary and secondary patterns. Identify critical path and control flow. Document iteration structure — what triggers a new iteration, whether count is statically known, and convergence criterion if applicable.

**Step 6 — Extract I/O behavioral hints.**
Re-read task code looking for: partial file access, format mismatch, small file overhead, unnecessary serialization, data reuse, checkpoint waste, metadata overhead. Requires reading both file-creation code and file-reading code side-by-side.

**Step 7 — Assemble and validate.**
Write `wdd.yaml`. Mark any assumption with `[ASSUMPTION]` in the field value AND add a confidence record in `translation_metadata`. Validate against the checklist in Section 6.

### Format-Specific Extraction Rules

| Source Format | Task extraction | Dependency extraction |
|---|---|---|
| Nextflow | `process` blocks | Channel connections between processes |
| Pegasus DAX | `<job>` elements | `<uses>` file elements on jobs |
| Parsl | `@python_app` / `@bash_app` decorators | `depends_on=` arguments |
| Slurm | Script steps, job arrays | `#SBATCH --dependency=` directives |
| Snakemake | `rule` blocks | `input:`/`output:` file matching across rules |
| Swift/T | `app` functions | Data-flow variable passing |

## 6. Validation Checklist

1. **Completeness** — every file read/written in the codebase is represented as a data object
2. **Consistency** — every `data_id` in task inputs/outputs appears in `data_objects`; every `task_id` in edges appears in `tasks`; every `task_id` in stages appears in `tasks`
3. **Pattern accuracy** — P-C pattern classifications match actual producer/consumer cardinalities
4. **No deployment leakage** — zero references to hardware, storage tiers, node counts, or performance targets
5. **Cross-reference integrity** — `cross_reference` index matches body content exactly
6. **Stage ordering** — `stage_execution_order` matches DAG dependencies
7. **Integrity hash** — `workflow_graph.integrity_hash` is current against `pc_edges`
8. **Assumption transparency** — every assumption has `[ASSUMPTION]` prefix AND a confidence record
9. **Multi-dataset edges** — edges carrying multiple datasets use the `data_objects` list; no duplicate edges for the same task relationship

## 7. Reference: Pattern Taxonomy

### P-C Patterns (per-edge)

| Pattern | Description | Example |
|---------|-------------|---------|
| `1_to_1` | One producer, one consumer | Simulation → post-processing |
| `1_to_n` | One producer shared across multiple consumers | Static input → many analysis tasks; scatter fan-out |
| `n_to_1` | Several producers → one consumer | Aggregation of parallel outputs |
| `n_to_n` | Multiple producers and consumers with shared I/O | Parallel ML training, ensemble workflows |

### Workflow-Level Patterns

| Pattern | Description | Typical P-C Structures |
|---------|-------------|----------------------|
| `cascading` | Linear chain of stages | Any |
| `iterative` | Repeats computation with prior output as input | Often 1_to_1; may include others |
| `scatter_gather` | Fan-out to parallel tasks, fan-in to aggregator | 1_to_n scatter; n_to_1 gather |
| `pipeline` | Stages overlap in time with streaming data | 1_to_1 or 1_to_n with loose coupling |
| `broadcast` | One task provides shared input to many | 1_to_n |
| `checkpointing` | Saves task state for restart/recovery | Usually 1_to_1 or n_to_1 |
| `conditional` | Tasks execute only if a runtime condition is met | Usually 1_to_1 or 1_to_n |
| `hybrid` | Combination of the above | Mixed |

## 9. Corner Cases

**Multi-dataset edges.** A single P-C edge may carry multiple data objects simultaneously (e.g., the openmm→aggregate edge in DeepDriveMD carries four HDF5 datasets in one file). Use the `data_objects` list on pc_edges. Do not create one edge per dataset for a single task relationship.

**Config/parameter objects.** Use `category: config` for parameter files and run configs. This prevents agents from treating configs as intermediate data to be staged or cleaned up.

**Conditional patterns.** Workflows where tasks only execute based on a runtime condition should include `conditional` in `secondary_patterns` for hybrid workflows. Document the branch logic in `control_flow.conditional_description`.

**Partial file access.** When a task reads only a subset of a file's datasets, always create an `io_behavioral_hints` entry with `potential_concern: partial_access`. Requires reading both the file-creation code and the file-reading code side-by-side — the most commonly missed finding in static analysis.

**Broadcast vs. scatter.** Both are `1_to_n` patterns. Broadcast: each consumer reads the full dataset (add a `data_reuse` hint). Scatter: each consumer reads a different partition. Distinguish in `data_flow_description` and `pc_pattern_rationale`.

## 10. Open Design Decisions

The following fields have unresolved trade-offs. Current schema implements the pragmatic default for each.

| Field | Current default | Alternative | Trade-off summary |
|-------|-----------------|-------------|-------------------|
| Loop annotation | Prose `iteration_description` in `control_flow` | Structured schema: `loop_type`, `bound_type`, `convergence_condition`, `max_iterations_guard` | Prose is more accurate in practice; structured enables machine-comparison by downstream agents |
| When a task reads/writes relative to its compute | Prose `behavioral_notes` per task | Structured `io_phase`, `burstiness`, `overlap_potential` per task | Prose is more accurate from static analysis; structured enables programmatic anomaly detection |
