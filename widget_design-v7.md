# Workflow Definition Document (WDD) — Design Specification
# Version: 7.0  |  Part of the WIDGET Six-Document Architecture
# See WIDGET_conventions.md for ID namespace, field status codes, and design principles.

---

## 1. Purpose & Scope

The WDD captures the **logical structure** of a scientific workflow — what it *is*, independent of how it is deployed. It is the most stable document in the architecture and changes only when workflow source code changes.

**Formal relationships:**
```
EDD  = f(WDD, scientist_input)
DDD  = prescription(WDD, EDD, GD, HRD)
IODD = execution(WDD, EDD, DDD, HRD, GD)
```

The WDD is generated by giving a workflow codebase to a static analysis agent (e.g., Claude Code). Everything in the WDD must be derivable from static analysis — no profiling data, no hardware specifics, no deployment decisions.

**What belongs in the WDD:** stage structure, task catalog (with behavioral notes, parallelism model, hardware path annotations, I/O access type, restart model), data object registry (format hints, cardinality source, lifecycle), producer-consumer edges, workflow graph, workflow-level pattern classification, I/O behavioral hints, execution profiles, generation provenance.

**What does not belong in the WDD:** storage tier assignments, node counts, memory allocations, placement policies, operator goals, per-run I/O profiles, resolved parameter values, job scheduler directives, environment modules, or concrete cardinality counts for input-determined data objects. Those belong in DDD, HRD, GD, IODD, and EDD respectively.

## 2. Field Status Model

| Status | Meaning |
|---|---|
| `required_static` | Extract from source via static analysis. If extraction fails, escalate to `required_static_ask`. |
| `required_static_ask` | Cannot be reliably inferred from code. Agent **must** prompt the scientist. |

**Completeness Gate** — before WDD is considered complete:
- All `required_static` and `required_static_ask` fields are non-null
- `workflow_graph.integrity_hash` is current against `pc_edges`
- `required_task_sets` in execution_profiles were auto-derived (never manually specified)
- `translation_metadata.field_confidence_records` has one entry per agent-inferred field
- Any `requires_human_review: true` field has been reviewed or explicitly deferred

---

## 2.1 Output Format (Canonical Form)

Authoring agents **must emit the canonical form** — see WIDGET_conventions §4 and template_WDD.yml OUTPUT FORMAT. Do not include in the output:

- **Authoring-only keys:** `_status`, `_prompt`, `_quality_check`, `_extract`, `_entry`, or any other `_*` keys (these are generation instructions, not document content)
- **`filled_by`** in `field_confidence_records` — provenance is in `metadata.generated_by` or `translation_metadata.translation_tool`
- **Comment lines** (lines beginning with `#`)

For fields using the `_value` pattern, emit only the parent key with the value directly (e.g. `workflow_description: "..."` not the nested structure). This reduces document size and token consumption for downstream consumers.

## 3. Document Structure

```
metadata            — identity, versioning, provenance
stages              — logical stage groupings (Section A)
tasks               — task catalog: behavioral, parallelism, hardware path,
                      I/O access type, restart model (Section B)
data_objects        — logical data registry: format hints, cardinality
                      source, lifecycle (Section C)
pc_edges            — producer-consumer edges with coupling and pattern (Section D)
workflow_graph      — derived DAG, control flow, cross-reference index (Section E)
workflow_patterns   — workflow-level pattern classification (Section F)
io_behavioral_hints — static-analysis-visible I/O concerns (Section G)
execution_profiles  — named partial execution subsets (Section H)
translation_metadata — generation provenance and confidence records (Section I)
```

## 5. Generation Procedure

**Step 1 — Survey codebase structure.**
Read the top-level directory, README, and orchestration files (Makefile, shell scripts, Nextflow `main.nf`, Pegasus DAX, Parsl app, Snakemake `Snakefile`, Slurm submission script). Identify: entry point, how stages/tasks are launched, configuration files.

**Step 2 — Identify all stages and tasks.**
Walk the orchestration layer. For each task: determine stage membership, read source code, note inputs and outputs.

**Step 3 — Classify I/O access types.**
For each task, inspect import statements and API calls:
- `from mpi4py import MPI` + `MPI.File.Open` → check for `Read_all`/`Write_all` (collective) vs. `Read`/`Write` (independent)
- `import h5py` + `driver='mpio'` → `hdf5_parallel`
- `from netCDF4 import Dataset` with parallel flag → `netcdf4_parallel`
- Standard Python file I/O or h5py without mpio → `python_serial`

**Step 4 — Classify restart models.**
For each task inspect: Is there a checkpoint file read at startup? Are there `--resume` / `--restart` CLI flags? Is there a "skip if output exists" guard? This determines `restart_model` and `restart_checkpoint_dataset`.

**Step 5 — Build the data object registry.**
Compile a deduplicated list of all data objects. Classify category and persistence. For HDF5/netCDF4, read file-creation code. Estimate cardinality from loop structures. Derive lifecycle fields from DAG topology.

**Step 6 — Map producer-consumer edges.**
For each data object, identify producers and consumers. Classify P-C pattern and coupling. Note multi-dataset edges.

**Step 7 — Analyze workflow-level patterns.**
From the DAG: classify primary and secondary patterns. Identify critical path and control flow.

**Step 8 — Extract I/O behavioral hints.**
Re-read task code looking for: partial file access, format mismatch, small file overhead, unnecessary serialization, data reuse, checkpoint waste, MPI-IO pattern risks.

**Step 9 — Assemble and validate.**
Write `wdd.yaml`. Mark any assumption with `[ASSUMPTION]` in the field value AND add a confidence record. Validate against Section 6 checklist.

### Format-Specific Extraction Rules

| Source Format | Task extraction | Dependency extraction |
|---|---|---|
| Nextflow | `process` blocks | Channel connections |
| Pegasus DAX | `<job>` elements | `<uses>` file elements |
| Parsl | `@python_app` / `@bash_app` | `depends_on=` arguments |
| Slurm | Script steps, job arrays | `#SBATCH --dependency=` |
| Snakemake | `rule` blocks | `input:`/`output:` file matching |
| Swift/T | `app` functions | Data-flow variable passing |

## 6. Validation Checklist

1. **Completeness** — every file read/written in the codebase is represented as a data object
2. **Consistency** — every `data_id` in task inputs/outputs appears in `data_objects`; every `task_id` in edges appears in `tasks`; every `task_id` in stages appears in `tasks`
3. **Pattern accuracy** — P-C pattern classifications match actual producer/consumer cardinalities
4. **No deployment leakage** — zero references to hardware, storage tiers, node counts, or performance targets
5. **Cross-reference integrity** — `cross_reference` index matches body content exactly
6. **Stage ordering** — `stage_execution_order` matches DAG dependencies
7. **Integrity hash** — `workflow_graph.integrity_hash` is current against `pc_edges`
8. **Assumption transparency** — every assumption has `[ASSUMPTION]` prefix AND a confidence record
9. **Multi-dataset edges** — edges carrying multiple datasets use the `data_objects` list; no duplicate edges for the same task relationship
10. **I/O access types** — every task has a non-null `io_access_type` (use `unknown` only with confidence record)
11. **Restart models** — every task has a non-null `restart_model`

## 7. Reference: Pattern Taxonomy

### P-C Patterns (per-edge)

| Pattern | Description | Example |
|---|---|---|
| `1_to_1` | One producer, one consumer | Simulation → post-processing |
| `1_to_n` | One producer shared across multiple consumers | Static input → many analysis tasks |
| `n_to_1` | Several producers → one consumer | Aggregation of parallel outputs |
| `n_to_n` | Multiple producers and consumers with shared I/O | Parallel ML training |

### Workflow-Level Patterns

| Pattern | Description | Typical P-C Structures |
|---|---|---|
| `cascading` | Linear chain of stages | Any |
| `iterative` | Repeats computation with prior output as input | Often 1_to_1 |
| `scatter_gather` | Fan-out to parallel tasks, fan-in to aggregator | 1_to_n scatter; n_to_1 gather |
| `pipeline` | Stages overlap in time with streaming data | 1_to_1 or 1_to_n with loose coupling |
| `broadcast` | One task provides shared input to many | 1_to_n |
| `checkpointing` | Saves task state for restart/recovery | 1_to_1 or n_to_1 |
| `conditional` | Tasks execute only if a runtime condition is met | 1_to_1 or 1_to_n |
| `hybrid` | Combination of the above | Mixed |
