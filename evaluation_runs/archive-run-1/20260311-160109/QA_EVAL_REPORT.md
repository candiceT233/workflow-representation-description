## 3. WDD Losses: What Is the Issue?

### 3.1 Largest WDD Losses (Knowledge >> WDD)

#### q018: How are logical file names mapped to actual data locations? (WDD 2 vs WK 5, diff -3)

| Context | Score | Model Answer |
|---------|-------|--------------|
| **Knowledge** | 5 | "The mapping is handled by the **Pegasus ReplicaCatalog**. The context references it in the Validation Points table... The ReplicaCatalog maps the logical names used within the workflow DAG (e.g., `ALL.chrX.250000.vcf`, `columns.txt`) to these physical file locations so Pegasus can locate and stage the data at execution time." |
| WDD | 2 | "The WDD does not specify how these logical names are mapped to actual file paths or data locations on disk. The `cardinality_source` fields reference controlling parameters... but the physical path resolution mechanism is not documented in this WDD." |

**Root cause:** The WDD has no field for Replica Catalog or LFN→PFN mapping. The knowledge document includes a "Validation Points" table with "ReplicaCatalog | At runtime" for column file and VCF checks. The WDD template does not capture Pegasus-specific runtime catalog semantics.

---

#### q014: How does the pipeline generate the baseline data? (WDD 2 vs WK 4, diff -2)

| Context | Score | Model Answer |
|---------|-------|--------------|
| **Knowledge** | 4 | "The **Frequency task** generates the baseline through **Monte Carlo random sampling**. It repeatedly selects random subsets of **52 individuals** from a population (**1,000 iterations**) and computes mutation overlap for each sample. Aggregating these results establishes a **null distribution**... The frequency-derived distribution provides the expected range for common variation." |
| WDD | 2 | "The WDD describes... **Allele frequency filtering** (Individuals task)... **SIFT pathogenicity scoring** (Sifting task)... **Mutation Overlap** computes pairwise overlap... **Frequency** measures how often overlapping mutations occur across randomly sampled individuals... However, the WDD does not describe an explicit classification step that labels variants as 'disease-associated'." |

**Root cause:** The WDD frequency task description says "applies random sampling" and "performs random sampling via random.sample()" but does not specify the Monte Carlo parameters: **52 individuals, 1000 runs**. The knowledge document explicitly states "n_indiv=52, n_runs=1000" in the processing logic. The WDD conflated allele frequency + SIFT with the null distribution; the reference expects the Monte Carlo mechanics.

#### q061: Which software tools for imputation and phasing in Phase 3? (WDD 1 vs WK 3, diff -2)

| Context | Score | Model Answer |
|---------|-------|--------------|
| **Knowledge** | 3 | "The context mentions that the input VCF files have filenames containing `phase3_shapeit2_mvncall_integrated_v5`, which hints that **SHAPEIT2 and MVNcall** were used upstream for phasing and imputation." |
| WDD | 1 | "The WDD does not contain information about imputation and phasing tools used in Phase 3. The document describes the downstream analysis workflow... but does not cover the upstream imputation and phasing steps." |

**Root cause:** The WDD `data:sift_annotation_vcf` and `data:vcf_input` descriptions do not include the actual filename pattern `phase3_shapeit2_mvncall_integrated_v5`. The knowledge document lists the full VEP filename `ALL.chrX.phase3_shapeit2_mvncall_integrated_v5.20130502.sites.annotation.vcf`, which allows inference of upstream tools. The WDD uses abstract data IDs without filename hints.

#### q070: What categorical framework does the "Populations" task provide? (WDD 2 vs WK 4, diff -2)

| Context | Score | Model Answer |
|---------|-------|--------------|
| **Knowledge** | 4 | "There is no task called 'Populations'... **Population files** serve as workspace inputs... The categorical framework they provide is a **grouping of individuals into population/ancestry groups** — ALL, EUR, EAS, AFR, AMR, SAS, GBR... This grouping drives the analysis structure... Mutation_Overlap and Frequency tasks are launched for each (chromosome, population) pair." |
| WDD | 2 | "The WDD YAML does not define a 'Populations' task. The workflow contains five tasks... None of these is named or described as a 'Populations' task. Population membership information is provided by **data:population_file**... The context does not contain enough information to answer about a 'Populations' task specifically, because no such task exists." |

**Root cause:** The reference answer expects a "Populations" task that "downloads demographic metadata." The actual workflow has no such task—population files are config inputs. Both documents correctly explain this, but the knowledge answer emphasized the *categorical framework* (grouping, per-population analysis) and received a higher score. The WDD answer was more literal ("no Populations task") and under-explained the role of population_file in structuring analysis.

| **WDD** | 5 | "According to the WDD, the core executable scripts are located in the `bin/` directory. The five executables listed are: `bin/individuals.py`, `bin/individuals_merge.py`, `bin/sifting.py`, `bin/mutation_overlap.py`, `bin/frequency.py`" |

## 6. Recommendations for template_WDD.yml

### 6.1 Add Replica Catalog / Catalog Mapping (Pegasus)

**Recommendation:** For Pegasus workflows, add an optional field:

```yaml
catalog_mapping:
  _status: optional_static
  _extract: >
    For Pegasus: how logical file names (LFNs) map to physical paths (PFNs).
    E.g., "ReplicaCatalog maps LFN to PFN at runtime; paths from --dataset, --src-path."
    For Nextflow/Snakemake: how input paths are resolved (e.g., params, config).
  _value: null
```

**Rationale:** Addresses q018; enables "how are logical names mapped to data locations?" Q&A.

### 6.2 Enrich Frequency / Null-Distribution Task with Sampling Parameters

**Recommendation:** When a task establishes a null distribution via random sampling, capture parameters:

```yaml
sampling_parameters:
  _status: optional_static
  _extract: >
    If task uses Monte Carlo / random sampling (e.g., null distribution):
    n_samples, n_runs, sampling_method. E.g., "n_indiv=52, n_runs=1000".
  _value: null
```

**Rationale:** Addresses q014, q042; the reference expects "selecting random individuals" with concrete numbers.

### 6.3 Add filename_pattern or source_hint to Data Objects

**Recommendation:** For input data_objects, add:

```yaml
filename_pattern:
  _status: optional_static
  _extract: >
    Actual filename pattern when derivable from code/config (e.g., ALL.chrX.phase3_shapeit2_mvncall_integrated_v5).
    Enables inference of upstream tools (SHAPEIT2, MVNcall) and data provenance.
  _value: null
```

**Rationale:** Addresses q061; filename hints support upstream tool inference.

### 6.4 Enrich population_file / Config Data Descriptions

**Recommendation:** For config inputs that define categorical groupings:

```yaml
_extract: >
  ... Include: "Provides categorical framework for per-population analysis; groups individuals
  into ancestry populations (ALL, AFR, EUR, ...); consumed by mutation_overlap and frequency
  for (chromosome, population) scoped analysis."
```

**Rationale:** Addresses q070; clarifies role when reference expects a "Populations" task.
